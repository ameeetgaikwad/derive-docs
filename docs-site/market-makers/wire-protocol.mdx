Wire format is JSON. **All bigints travel as decimal strings**; all on-chain quantities are 18dp integers; timestamps named `*At` are **milliseconds** epoch, `expiry` fields are **unix seconds**.

## Endpoints

| Channel | Path | Who |
|---|---|---|
| Maker WS | `ws://<host>:<port>/maker` | you |
| Taker WS | `ws://<host>:<port>/taker` | retail frontend |
| REST | `POST /rfq`, `GET /rfq/:id`, `POST /rfq/:id/accept`, `GET /health` | takers / status polling |

Default port is **3030** (`RFQ_PORT`/`PORT` env on the engine); the listen address is set with `HOST` (default `127.0.0.1`). The reference bot default is `RFQ_ENGINE_WS=ws://127.0.0.1:3030/maker`.

<Note>
**Production posture:** the engine deliberately does not terminate TLS in-process — it sits behind a **TLS-terminating reverse proxy**. Makers connect to `wss://<host>/maker`, takers to `https://<host>/rfq` + `wss://<host>/taker`. Ask the team for the current testnet hostname; the plain-HTTP port is never exposed publicly.
</Note>

`GET /rfq/:id` and `GET /health` are unauthenticated; makers may poll RFQ status over REST too.

Taker-side RFQ creation is gated by the engine — neither gate affects the maker channel:

- `TAKER_OPEN=false` rejects all RFQ creation (REST `403` / taker-WS error).
- Creations are **rate-limited per IP** (`RFQ_RATE_LIMIT_PER_MIN`, default 30/min); over-limit requests get `429` / `rate limit exceeded — slow down`.

## Auth handshake (maker WS)

Immediately on connect the server sends a challenge:

```json
{ "type": "auth_challenge",
  "challenge": "Hedge rfq-engine maker auth 1c1f7b3e-83b7-4d54-9f3e-0db1b15c2f11 1781770000000" }
```

The challenge is `Hedge rfq-engine maker auth <uuid> <ms-timestamp>`, unique per connection. You sign it as an **EIP-191 personal message** (`personal_sign` / viem `account.signMessage` — *not* EIP-712) with the EOA that owns your subaccount, and reply:

```json
{ "type": "auth", "address": "0x5c9Ca4A3f39Cf36C968402C8E933cB2979882BF8", "signature": "0x..." }
```

On success:

```json
{ "type": "auth_ok", "address": "0x5c9Ca4A3f39Cf36C968402C8E933cB2979882BF8" }
```

…followed immediately by a **replay of every currently-open RFQ** as individual `rfq_open` frames, so reconnects never miss live auctions. On a bad signature you get `{ "type": "error", "message": "auth failed: bad signature" }` and remain unauthenticated (the socket is not closed). Sending a quote before authenticating yields `{ "type": "error", "message": "authenticate first" }`.

<Warning>
**Maker allowlist.** When `MAKER_ALLOWLIST` is set on the engine (it is on the shared testnet engine), an address not on it gets `{ "type": "error", "message": "auth failed: address not allowlisted" }` and the socket is closed with code **4003**. Register your maker address with the team first — see [Onboarding](/market-makers/onboarding#what-you-need).
</Warning>

Two session-management behaviors to build for:

- **One live connection per maker address.** When the same address authenticates on a new socket, the old socket receives `{ "type": "superseded", "message": "..." }` and is closed with code **4000**. A superseded client must **not** auto-reconnect — it would supersede the new session right back (the reference client stops on `superseded`).
- **Heartbeat.** The server sends protocol-level WS pings every `WS_HEARTBEAT_MS` (default 30 s) and terminates a connection that has neither ponged nor sent any frame for one full interval. Standard WS stacks (browsers, Node/undici, `ws`) answer pings automatically — there is no app-level keepalive message, and none is needed.

Re-authenticate on every reconnect (new challenge each time). The reference client reconnects with exponential backoff (1 s doubling to 30 s) — except after `superseded`, where it stops.

## RFQ broadcast

Every new auction is pushed to all authenticated makers:

```json
{
  "type": "rfq_open",
  "rfq": {
    "id": "501329a3-aa90-45cd-8607-f37f8439971d",
    "takerSubaccountId": "6",
    "direction": "sell",
    "instrument": {
      "name": "BTC-20260619-69000-C",
      "currency": "BTC",
      "optionAsset": "0xD0dD8DcA596540F615e66E07F49d40647D8bC6eD",
      "expiry": "1781856000",
      "strike": "69000000000000000000000",
      "isCall": true,
      "subId": "39614110892406511198553831168"
    },
    "amount": "1000000000000000000",
    "createdAt": 1781770000000,
    "auctionEndsAt": 1781770008000,
    "acceptDeadlineAt": null,
    "status": "open"
  }
}
```

Field notes:

| Field | Meaning |
|---|---|
| `id` | UUID — the key for everything that follows |
| `direction` | v1: always `"sell"` (taker sells, you buy) |
| `instrument.expiry` | unix **seconds** |
| `instrument.strike` | 18dp (here: 69,000) |
| `instrument.subId` | option subId encoding — see [Signing § subId encoding](/market-makers/signing#option-subid-encoding) |
| `amount` | 18dp option size (here: 1.0) |
| `auctionEndsAt` | ms epoch — quotes accepted **strictly before** this |
| `acceptDeadlineAt` | ms epoch taker-accept deadline; `null` until the auction closes with a winner |
| `status` | `open\|closed\|expired\|executing\|executed\|failed` |

## Quote submission

A quote is nothing but your **fully signed EIP-712 Action targeting RfqModule** (construction in [Signing](/market-makers/signing)). One message:

```json
{
  "type": "quote",
  "rfqId": "501329a3-aa90-45cd-8607-f37f8439971d",
  "action": {
    "subaccountId": "5",
    "nonce": "1781770003123456",
    "module": "0x2769E33b2169C83304cEa0c5C8fbC5a1707E305D",
    "data": "0x...",
    "expiry": "1781770368",
    "owner": "0x5c9Ca4A3f39Cf36C968402C8E933cB2979882BF8",
    "signer": "0x5c9Ca4A3f39Cf36C968402C8E933cB2979882BF8"
  },
  "signature": "0x..."
}
```

- `subaccountId` — **your** maker subaccount
- `module` — the RfqModule address
- `data` — `abi.encode(RfqOrder{maxFee, trades[]})`
- `expiry` — unix seconds; must outlive `auctionEndsAt`
- `signer` — v1: must equal `owner`
- `signature` — 65-byte EIP-712 signature

The server replies with exactly one of:

```json
{ "type": "quote_ack", "rfqId": "501329a3-...", "quoteId": "8a2b4c..." }
{ "type": "quote_rejected", "rfqId": "501329a3-...", "reason": "<human-readable reason>" }
```

### Replace and cancel

**Replace** — a second quote from the same maker on the same RFQ **replaces** the previous one (only the latest is kept). The ack then carries the id of the quote it displaced:

```json
{ "type": "quote_ack", "rfqId": "501329a3-...", "quoteId": "9b3c5d...", "replacedQuoteId": "8a2b4c..." }
```

**Cancel** — `{"type":"cancel","quoteId":"8a2b4c..."}` withdraws a live quote while its auction is still open. The server replies with exactly one of:

```json
{ "type": "cancel_ack", "rfqId": "501329a3-...", "quoteId": "8a2b4c..." }
{ "type": "cancel_rejected", "quoteId": "8a2b4c...", "reason": "auction window closed — quote can no longer be cancelled" }
```

`cancel_rejected` covers unknown/foreign quote ids and the closed-auction case — once the window ends, the winning quote is locked in until the taker-accept deadline or your `action.expiry`. Cancel/replace immediately release the collateral the engine had reserved against the quote.

### Validation, in the exact order the engine runs it

1. RFQ exists and is `open`; clock strictly before `auctionEndsAt` (`unknown rfq ...`, `rfq ... is closed`, `auction window closed`).
2. Action shape: `action.module` == RfqModule; `action.owner` == your authenticated WS address; `signer == owner`; `subaccountId != 0`; `action.expiry` in the future **and** `>= ceil(auctionEndsAt/1000)` (`action.expiry must outlive the auction window`).
3. `action.data` ABI-decodes as `RfqOrder` with **exactly one trade**, and that trade matches the RFQ exactly: `trade.asset == instrument.optionAsset`, `trade.subId == instrument.subId`, `trade.amount == +rfq.amount` (positive — you receive what the taker sells), `trade.price > 0`.
4. EIP-712 signature recovers to `action.signer` (`invalid EIP-712 signature`).
5. On-chain reads: `Matching.subAccountToOwner(action.subaccountId)` must equal your address (`subaccount N is not deposited into Matching by 0x...`), and your cash balance must cover the **fee-aware, reservation-aware** requirement `trade.price * trade.amount / 1e18 + maxFee + estimated SRM OI fee + cash reserved by your other live quotes` (`insufficient maker cash: balance X < required Y (incl. OI fee Z) + reserved R across open quotes`). A failed feed read for the OI fee estimate also rejects (`cannot estimate SRM OI fee ...`).
6. After the chain reads, the window is re-checked — a quote that straddles the close is rejected with `auction window closed`. **Budget your latency: RPC round-trips happen inside the window.**

<Note>
- Re-quoting the same RFQ **replaces** your previous quote (only the latest counts; the ack carries `replacedQuoteId`). To withdraw entirely, send `cancel` while the auction is open. The reference bot quotes once per RFQ.
- The OI fee estimate uses the same math as the chain, with `OIFeeRateBPS`, the forward price, and `minOIFee` read live on every quote — see [Fees](/reference/fees). Reserved cash spans all your open auctions plus won-quotes awaiting taker accept, and is released on cancel/replace/loss/execution/failure/deadline-expiry.
- Quotes are sealed: nothing about competitor quotes is sent to you while the auction is open.
</Note>

## Auction close, win/loss, execution

When the window ends, **every** authenticated maker receives:

```json
{ "type": "rfq_closed",
  "rfqId": "501329a3-...",
  "bestQuoteId": "8a2b4c...",
  "won": true,
  "acceptDeadlineAt": 1781770128000 }
```

- `bestQuoteId` is `null` if zero valid quotes arrived (the RFQ status moves to `expired`).
- `won: true` is present **only on the winning maker's socket**; there is no explicit `lost` flag — infer loss from the absence of `won`. Losing quotes stop reserving your collateral immediately.
- `acceptDeadlineAt` (winner only, ms epoch) is the **taker-accept deadline**: `TAKER_ACCEPT_DEADLINE_MS` on the engine, default **120 s** after close.
- Losers are **not** told the winning premium, only the winning `quoteId`.

If your quote won, the RFQ moves to `closed` and waits for the taker to accept before the deadline. The taker signs a `TakerOrder{orderHash, maxFee}` over the hash of *your* trades and POSTs it to `/rfq/:id/accept`; the engine then submits `Matching.verifyAndMatch` on-chain.

### Terminal notifications

**Executed** — on a successful on-chain fill, **all** authenticated makers receive a `rfq_executed` carrying the realized **fill report**:

```json
{ "type": "rfq_executed", "rfqId": "501329a3-...", "txHash": "0x2d5d7c88...",
  "fill": {
    "quoteId": "8a2b4c...",
    "instrument": "BTC-20260619-69000-C",
    "maker": "0x5c9C...",
    "makerSubaccountId": "5", "takerSubaccountId": "6",
    "amount": "1000000000000000000",
    "premium": "378586807763808053551",
    "totalPremium": "378586807763808053551",
    "makerFee": "0", "takerFee": "0",
    "blockNumber": "112792281" } }
```

(`premium` is per-unit 18dp; `makerFee`/`takerFee` are the module fees — zero today, see [Fees](/reference/fees).)

**Failed** — `{ "type": "rfq_failed", "rfqId": "...", "reason": "..." }` goes to the **winning maker** when execution reverts or errors after the taker accepted. A reverted execution does *not* burn your nonce, so the action technically remains valid until expiry.

**Expired** — `{ "type": "rfq_expired", "rfqId": "...", "reason": "taker did not accept before the deadline" }` goes to the **winning maker** when the taker misses `acceptDeadlineAt`. The RFQ moves to `expired`, your reserved collateral is released, and your signed action simply ages out at its `expiry`.

<Note>
The on-chain `RFQTradeCompleted`/`FeeCharged` events remain the authoritative record — reconcile against them, treating the fill report as operational convenience.
</Note>

## REST status (useful for reconciliation)

`GET /rfq/:id` → `200`:

```json
{
  "rfq": { "...": "PublicRfq as in the broadcast; status reflects lifecycle; acceptDeadlineAt set once closed with a winner" },
  "quoteCount": 1,
  "bestQuote": {
    "quoteId": "8a2b4c...",
    "maker": "0x5c9C...",
    "makerSubaccountId": "5",
    "premium": "378586807763808053551",
    "totalPremium": "378586807763808053551",
    "orderHash": "0xda4e1328...",
    "trades": [ { "asset": "0xD0dD...", "subId": "3961411089...", "price": "3785868...", "amount": "1000000000000000000" } ],
    "actionExpiry": "1781770368"
  },
  "execution": { "txHash": "0x2d5d...", "status": "success", "blockNumber": "112792281" },
  "error": null
}
```

- `bestQuote` is `null` until the window closes with at least one quote; `premium` is per-unit 18dp, `totalPremium = premium × amount / 1e18`.
- `orderHash` is `keccak256(abi.encode(trades))` — what the taker signs.
- `execution` is `null` pre-execution; `error` is set when `status === "failed"` (and on a missed accept deadline: `status: "expired"`, `error: "taker did not accept before the deadline"`).

Error codes: `404` unknown RFQ; accept returns `409` on validation failure (including a passed accept deadline), `502` on on-chain failure, `200` on success. A successful accept returns `{ txHash, status, blockNumber, fill }` — the same fill report as the `rfq_executed` push.

The full lifecycle state machine is in the [overview](/market-makers/overview#rfq-lifecycle).

## WS close codes

| Code | Meaning |
|---|---|
| `4000` | Superseded — a newer connection authenticated for the same maker address. Do not auto-reconnect. |
| `4003` | Not allowlisted — register your maker address with the team, then reconnect. |
